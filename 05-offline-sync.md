# Offline and sync

## The constraint that shapes everything

There is no cell service where people fish. Not "sometimes patchy" — none, for hours, in
the places the product is most useful. Every architectural decision follows from this.

Offline is the **default state**, not the error state. There is no offline banner, because
that would be showing a banner most of the time the app is used. There are timestamps on
data instead.

## Client storage

- Dexie over IndexedDB. Tables mirror the domain model plus `syncQueue` and `bundles`.
- **All writes go to IndexedDB first** and enqueue a sync op. The UI reads from IndexedDB
  only, never from the network directly. A screen that can render from cache always does.
- Position tracking writes to a ring buffer and downsamples before enqueueing: full rate
  in memory for the live depth display, 1 point per 10 s persisted, Douglas-Peucker
  simplified on trip close.
- Storage budget: warn at 80% of the quota, offer per-trip archive-and-purge. A season of
  tracks will fill a phone if you let it.

## The dock bundle

Before departure, over wifi, the boat pulls one signed blob per region and 48h window:

```
bundle-<regionId>-<startIso>.json.gz
  ├── tides[]           predictions, full window
  ├── currents[]        predictions per station
  ├── forecast          with issuing office and issue time
  ├── regs              snapshot with fetchedAt
  ├── sunMoon           precomputed, though the engine can also derive it
  ├── bathyTileRefs[]   tile keys already in the cache
  └── meta              generatedAt, expiresAt, schemaVersion, signature
```

Generated by the `bundles` BullMQ job on a schedule, cached in Redis, served from a single
`GET /bundles/:regionId`. Bundle generation must be deterministic given its inputs so the
same request does not produce a new blob and force a redownload.

The UI surfaces bundle age prominently and prompts at the dock: "last updated 3 days ago,
tap to refresh before you leave."

## Sync

- **Ids are client-generated ULIDs.** The server never assigns identity. This is
  non-negotiable when records are created hours before they are ever transmitted.
- **Catches and TrackPoints are append-only events.** They are never updated, only
  superseded by a correction event carrying `supersedesId`. This makes the highest-volume
  tables conflict-free by construction.
- Mutable entities (Rig, GearItem, Spot, Boat) use per-field last-write-wins with an
  `updatedAt` per field. Conflicts are rare and low-stakes.
- Sync is a single idempotent `POST /sync` taking a batch of ops and a cursor, returning
  ops the client has not seen. Retry-safe by op id. Partial success is normal: the server
  returns per-op results and the client dequeues only the accepted ones.
- Batches are size-capped and resume mid-batch. A boat coming back into range on a marginal
  1-bar connection is the normal case, not the edge case.

## Failure behavior

- A sync failure is never a modal. It is a small persistent indicator with a retry.
- Never block trip logging on auth. If the token expired at sea, keep logging and
  reauthenticate on return.
- Never lose data to a schema migration. Migrations are additive; the client keeps
  unrecognized fields and round-trips them.
